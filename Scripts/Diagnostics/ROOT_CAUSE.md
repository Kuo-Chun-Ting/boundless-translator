# 大段取消後，短句翻譯變慢的原因

2026-09-26，macOS 26.5.2 (25F84)、Xcode 26.6，英文 → 繁體中文。所有實驗直接呼叫 Apple Translation framework，不啟動 Boundless Translator。測資來自 `Tests/Fixtures/Translation/100K_words.txt`，短句固定為 `THE CITY THAT LEARNS`。

## 結論

在這台 Mac 與這個語言配對上，已送出的單次大段翻譯沒有被立即中斷，後面的短句仍受 Apple 背景翻譯服務影響。取消 session、取消 Swift 工作，甚至讓短句由另一個程序送出，都無法立即消除等待。

App 的取消接點確實有作用：清掉目前請求、呼叫 session 取消、忽略舊結果。但這些動作不能保證 Apple 當下的翻譯運算立刻停止。產品缺少對單次輸入量的限制，放大了這個限制的影響。

這不是「cancel() 本身執行了十幾秒」。取消函式很快返回，等待發生在後面的 `translate` 呼叫。

## 對照結果

取同一篇測資前 65,000 個字元。原始內容為 ASCII，因此此處字元數也等於 UTF-8 位元組數。先暖機，再開始大段，約 2.7 秒後送四個字：

| 大段處理方式 | 後面的四個字 | 大段呼叫結果 | 大段返回後再翻四個字 |
| --- | ---: | --- | ---: |
| 不取消 | 16.90 秒 | 約 19.62 秒後返回譯文 | 0.052 秒 |
| 只取消 session | 16.82 秒 | 約 19.63 秒後仍返回譯文 | 0.045 秒 |
| 只取消 Swift 工作 | 16.99 秒 | 約 19.73 秒後拋出取消錯誤 | 0.046 秒 |
| 兩者都取消 | 17.27 秒 | 約 19.94 秒後拋出取消錯誤 | 0.048 秒 |

大段請求仍在執行時，測試程式的主執行緒每秒正常執行，最大間隔約 1.07 秒。因此這些十幾秒的等待不是測試程式阻塞主執行緒造成。

原始紀錄位於 `Build/TranslationDiagnostics/`：

- `run-20260926-180950.tQhkNE/concurrent.log`
- `run-20260926-181011.33gD7p/cancel.log`
- `run-20260926-181031.E7dLaC/task-cancel.log`
- `run-20260926-180905.GyHItt/cancel-both.log`

### 取消狀態確實有設定

取消後，再對同一個 session 發出短句，它約 0.0005 秒就回報 `TranslationError.alreadyCancelled`。但先前已送出的工作仍等待到約 20 秒才返回。這排除了「取消呼叫沒生效、或取消了錯誤的 session」的解釋。

### 另一個程序也受影響

另一個獨立程序翻短句，平常只要 0.156 秒；當第一個程序的大段已呼叫取消、但尚未返回時，同樣短句需要 18.243 秒。紀錄：`process-isolation.faDH5V/` 下的 `independent-baseline.log`、`independent-during-long.log`、`long-client.log`。

這排除了 Boundless 或診斷程式內部把兩筆請求排成隊列的解釋；等待跨越程序，發生在 Apple 的共用服務側。

### Apple 仍在運算

18:09:23 起取樣 Apple 的 `translationd` 三秒。這時取消已在 18:09:08 發出，大段直到 18:09:26 才返回。取樣包含 `EMTTranslator`、`PDecTranslator::translate`、`TranslationBeamSearch`、`Encdec::StartFeedforward` 與 Espresso 運算堆疊；程序狀態約為 100% CPU。

紀錄：`run-20260926-180905.GyHItt/translationd.sample.txt`。取樣證明取消後服務仍在翻譯運算，但不能據此斷定 Apple 所有翻譯都是單執行緒，或知道其內部所有排程與取消檢查的位置。

前一次完整十萬英文單字的對照，短句在約 93 秒返回，大段在約 212 秒才返回。這也表示不能描述成「所有短句一定要等整篇長文結束」。可確認的是舊工作持續消耗翻譯服務的處理時間、干擾新工作；不是已證明整個 API 只用一條執行緒。

## 改變工作量的結果

在大段開始 0.1 秒後，同時取消兩者，再送短句：

| 單次送出的大小 | 短句耗時 |
| --- | ---: |
| 2,000 字元 | 0.612 秒 |
| 5,000 字元 | 1.532 秒 |
| 10,000 字元 | 3.049 秒 |

同樣 65,000 字元改成每次只送 1,000 字元、收到結果才送下一段：2.7 秒後取消，第 8 段返回取消錯誤，不再送第 9 段；新短句約 0.052 秒返回。紀錄：`run-20260926-181126.IUTdN9/chunked.log`。

另在第 1 段開始 0.1 秒後取消，下一筆短句約 0.337 秒返回，退出代碼為 0，沒有送出第 2 段。紀錄：`run-20260926-181559.8eiA4y/chunked.log`。這排除了只在一段即將完成時取消，才看起來有效的情況。

縮小已交給 Apple 的單次工作量，能縮短取消後的等待。這支持以輸入上限或小段依序處理來解決，而不是增加取消呼叫或換一個程序。

較小的效能失敗對照使用 5,000 字元、開始 0.1 秒後取消。新版診斷以短句一秒內返回為標準，實測 1.607 秒，記錄 `passed=false` 並退出代碼 3。紀錄：`run-20260926-181321.Olo8TS/cancel-both.log`。正常短句約 0.057 秒，退出代碼 0，紀錄於 `run-20260926-181705.Xq9vLG/baseline.log`。這個失敗標準是我們的產品目標，不是 Apple 的契約。

## Apple 文件如何定義這件事

- [cancel()](https://developer.apple.com/documentation/translation/translationsession/cancel%28%29) 定義為嘗試停止 session 的工作，並說明取消後的新請求會拋錯。沒有承諾立即停止、固定取消時限或取消完成通知。
- [TranslationSession](https://developer.apple.com/documentation/translation/translationsession) 說明翻譯在使用者裝置上執行，並提供無介面的初始化方式。診斷使用的是這個公開 API。
- [Translating text within your app](https://developer.apple.com/documentation/translation/translating-text-within-your-app) 建議多筆字串使用批次 API，但未承諾批次中的工作可立即中斷。一次把所有小段送進批次，不能直接當成上述「一次一段」實驗的替代。

查閱的公開文件沒有公布可直接採用的單次最大字數，也沒有找到 Apple 對本次精確症狀的公開確認。等待行為沒有違反目前查到的取消承諾，但不符合我們要求的「取消後，下一筆短句立即恢復速度」。API 能返回完整譯文，也不等於適合承擔任意大的互動式請求。

## 建議處理順序

1. 先設定 App 的單次輸入大小上限。取得選字後、原文排版與 Apple 翻譯之前檢查；過大就提示「內容過長，請分段選取」，不默默截斷。用 UTF-8 大小作為可跨語言比較的度量，再依不同語言的實測訂上限，不能把上述英文數字當成所有裝置與語言的保證。
2. 若要在上限內接受較長文章，依句子或段落切成有大小上限的小段，每次只送一段。取消時停止剩餘段落、呼叫 session 取消並忽略舊結果。已送出的那一小段仍可能需要時間返回，不能宣稱零等待。
3. 保留逾時與取消處理，讓 UI 可離開並開始下一次操作。逾時只表示 App 不再等結果，不能宣稱 Apple 運算已停止，也不要自動重試大段而累積更多工作。
4. 回歸測試比較固定短句的正常耗時與「長文 → 取消 → 短句」耗時；另測過大內容是否在排版、送出前被拒絕，以及後續小段是否確實不再送出。

本次只修改診斷腳本與紀錄，沒有把上限或分段加入 App。開窗前的讀字與排版延遲是另一段流程，尚未因本實驗修正；朋友整個 App 無法操作的問題也不能據此直接視為同一根因。

## 後續採用的產品方案

依使用者 review，採用以 10,000 字元為目標的完整段落／句子分段，逐段翻譯與顯示，取消後停止未送出的段落；不採用上面研究階段建議的整篇輸入上限。開窗前不顯示額外載入提示；關閉翻譯視窗仍會取消當次翻譯，新翻譯不等待舊呼叫。單一超長句子仍完整保留，可能超過目標耗時。現行產品規格以 `spec.md` 為準。
